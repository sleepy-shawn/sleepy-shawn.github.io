Reasons for secrecy:

  • Competitive dynamics

  • Copyright liability

  • Before foundation models, data work meant heavy annotation of labeled data for supervised learning.

  • Now there’s less annotation, but there’s still a lot of curation and cleaning.

  • Data is fundamentally a long-tail problem and scales with human effort (unlike architectures and systems).

  • Pre-training: train on raw text (e.g., documents from the web)

  • Mid-training: train more on high-quality data to enhance capabilities

  • Post-training: train on chat transcripts or reinforcement learning

Key question: can you train a good model using only permissively-licensed data?#

Subtleties:

  • License laundering: redistribute copyrighted work under permissive license (hard to detect)

  • Collection licenses (Dolma is ODC-By) don’t extend to individual works

  • The status of synthetic data from LMs trained on unlicensed data is unclear

Data pipeline#

HTML to text is the main one

Inherently lossy: we need to linearize because HTML is tree-based

Tools are rule-based

Fine-to-PDF: from Common Crawl, OCR using a VLM or Docling, truncated PDFs, cleanup and filtering, layout info is missing

Filtering: language quality , toxicity

Classifier:

  1. Generative model (KenLM)
  2. Simple classifier

Model-based filtering is becoming the norm

gpt3: positive samples from {Wikipedia, WebText2, Books1, Books2}, Negatives: samples from CommonCrawl

Train a linear classifier based on word features

Keep documents stochastically based on score

Scale-dependent effects of filtering:

  • No single optimal threshold for filtering

  • If training for longer, want more (lower quality) data

  • If training for shorter, want less (higher quality) data

Summary:

  • Filtering is critical for building a good model

  • Recipe: define target data (what good looks like), extrapolate to raw data

Duplicate#

Two types of duplicates:

  • Exact duplicates (mirror sites, GitHub forks)

  • Near duplicates: same text differing by a few tokens

Deduplicating training data makes language models better

Design space:

  • What is an item (sentence, paragraph, document)?

  • How to match (exact match, existence of common subitem, fraction of common subitems)?

  • What action to take (remove all, remove all but one)?

Key challenge:

  • Deduplication is fundamentally about comparing items to other items

  • Need linear time algorithms to scale

Using a hash: MurmurHash

Exact deduplication#

  • Pro: simple, clear semantics, high precision

  • Con: does not deduplicate near duplicates

  • This code is written in a MapReduce way and can easily be parallelized and scaled

C4

Raffel+ 2019

  • Item: 3-sentence spans

  • How to match: use exact match

  • Action: remove all but one

Jaccard similarity = the NLP version of IoU#

Find near duplicates in linear time

MinHash = Minimum Hash

MinHash approximates Jaccard similarity, which can be used to estimate similarity

Locality-sensitive hashing#

We have to somehow sharpen the probabilities.

Solution: use n hash functions

Break up into b bands of r hash functions each (n = b * r)

The AND-OR structure of the bands sharpens the threshold

Data mixing#

Baselines:

  • Vibes: set p(s) manually based on intuition (quite common)

  • Uniform sampling: sample uniformly (p(s) ∝ 1)

  • Proportional mixing: sample proportionally to the number of tokens in a source (p(s) ∝ num_tokens(s))

However…

  • We want to ensure diversity (e.g., across incomparable sources: literature, code, papers)

  • Each source is finite, so if we put too much weight on a small source, then we need to epoch over it

50x epochs on high-quality data…can lead to overfitting!

Or increase the loss proportion of high-quality data

Unimax: regression-based mixing#

  • Define a distribution over mixtures p (e.g., Dirichlet)

  • Define a regression method (e.g., linear, gradient boosted trees)

  • Define a target based on downstream evals (careful not to overfit!)

  • Discrepancy between small and large scales (tradeoff between cost and accuracy)

  • Important consideration: epoching and overfitting (solution: cap or simulate)
