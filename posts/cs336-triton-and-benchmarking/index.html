Programming Model#

A thread block is a collection of threads that access the same shared memory.

A thread block is scheduled on one SM. There are 32 threads per warp.

All threads within a warp must execute the same instructions in lockstep on an SM. With control divergence, if different threads in a warp need to execute different instructions (if A, else B), the instructions must be executed sequentially (bad).

In Triton, we think from a thread block perspective.

An SM runs multiple warps and switches between them at zero cost.

Warp Occupancy#

Each thread can use between 0 and 255 registers.

The more registers threads use, the fewer threads can be scheduled on an SM, which means lower occupancy.

Bank Conflicts#

Shared memory is divided into 32 banks, each 4 bytes wide.

The issue is that in each cycle, each bank can only be accessed by one thread if the threads access different locations.

As a result, if multiple threads access different locations in the same bank, the accesses are serialized (a bank conflict).

In the worst case, consider a matrix where each row spans all banks. Having 32 threads access the first column results in a 32-way bank conflict because each thread accesses bank 0.

Swizzling rearranges shared memory.

Coalescing#

When the 32 threads in a warp access HBM, memory accesses are combined into transactions of 128 bytes.

In the best case, with full coalescing, all threads access the same cache line.

Block Occupancy#

Thread blocks are scheduled onto SMs in waves.

The B200 has 148 SMs. If we launch 160 thread blocks, the first wave has 148 blocks and the second wave has 12 blocks.

The second wave has poor occupancy, leaving some SMs idle.

Benchmarking and Profiling#

Benchmarking measures the wall-clock time it takes to perform an operation.

It only gives you the end-to-end time. Profiling shows where that time is spent.

torch.cuda.synchronize() lets the CPU wait for the GPU.

Use CUDA events for timing.

Triton#

Specify what each thread does.

The conceptual framework is to load data into shared memory, operate on it, and write it back to global memory.

@triton.jit
def triton_gelu_kernal(x_ptr, y_ptr, num_elements, BLOCK_SIZE: t1.constexpr):
    pid = tl.program_id(axis=0)
    start = pid * BLOCK_SIZE

    # Indices where this thread block should operate
    offsets = start + tl.arrange(0, BLOCK_SIZE)

    mask = offsets < num_elements

    x = tl.load(x_ptr + offsets, mask=mask)
    # Approx gelu is 0.5 * x * (1 + tanh(sqrt(2/pi) * (x + 0.044715 * x^3)))
    # Compute (tl.tanh doesn't exist, use tanh(a) = (exp(2a) - 1) / (exp(2a) + 1)
    a = 0.79788456 * (x + 0.044715 * x * x * x)
    exp = tl.exp(2 * a)
    tanh = (exp - 1) / (exp + 1)
    y = 0.5 * x * (1 + tanh)

    # Store
    tl.store(y_ptr + offsets, y, mask=mask)

Another Useful Expression#

block_size = triton.next_power_of_2(N)

In the sum example, the row doesn’t fit in a block.

The strategy:

  1. Break up rows into tiles.
  2. Each thread iterates over the tiles and accumulates a sum.
  3. Perform a final reduction over the accumulators of all threads.

The Key Idea of Tiling#

Recall that each matrix is linearized in memory.

a.stride(0) # a's col num
a.stride(1) # a's row num
